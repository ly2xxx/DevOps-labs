Inside the K8s Fix-It Agent
01

One Question, End to End

You type "why is my pod crashing?" Here's everything that happens before an answer comes back.

What this thing actually does

This project is a chat window that can look inside a Kubernetes cluster, figure out what's broken, and, once you click Approve, actually fix it. It then checks its own work and tries again if the fix didn't take.

🔍

Diagnose

Reads pods, logs and events to find the real root cause, not a list of guesses.

📝

Propose

Writes a short, specific plan: "patch deployment X to image Y."

✋

Wait for you

Nothing changes on the cluster until a human clicks Approve.

✅

Apply & verify

Makes the change, waits, re-inspects, and retries up to 3 times.

🔧
Think of it as a mechanic who needs your signature

A good mechanic plugs in the diagnostic scanner, tells you what's wrong, hands you a work order, and only picks up a wrench once you sign. Then they test-drive the car before handing back the keys. This agent follows that exact script.

The AI never touches the cluster directly

The model only ever asks for a tool by name. Python code decides whether to run it, runs it, and hands back the result. That gap is where every safety check in this project lives, and you'll see it again in Module 4.

Stop 1: the forwarding desk

The browser never talks to Python directly. It calls /api/... on the same website, and a tiny Next.js file passes the request along. The file's odd name, [...path], means "catch every URL under /api/."

agent-interface/app/api/[...path]/route.ts 
async function proxy(req: NextRequest, path: string[]): Promise<NextResponse> {
  const target = `${backendUrl()}/api/${path.join("/")}${req.nextUrl.search}`;
  const init: RequestInit = {
    method: req.method,
    headers: { "Content-Type": req.headers.get("content-type") || "application/json" },
  };
PLAIN ENGLISH

Define a helper that takes an incoming request plus the pieces of its URL path.

Build the real address: the backend's base URL, then /api/, then the same path and any ?query bits the browser sent.

Start describing the outgoing request...

...using the same method (GET or POST) the browser used...

...and the same content type, defaulting to JSON.

Done describing it. The rest of the file sends it and copies the answer back.

🧭
Why bother with a middleman?

Because the browser only talks to one address, the Python backend can stay private inside the cluster, and you avoid CORS headaches. If the backend is down, this file returns a clear 502 error naming the address it couldn't reach.

Stop 2: the front desk opens a ticket

Inside Python, main.py is the reception area. Each endpoint is a door. This is the first one your question walks through.

agent-backend/app/main.py 
@app.post("/api/query")
def submit_query(request: QueryRequest):
    query = request.query.strip()
    if not query:
        raise HTTPException(status_code=400, detail="Query cannot be empty.")

    session_id = str(uuid.uuid4())
    config = {"configurable": {"thread_id": session_id}}
PLAIN ENGLISH

The incoming body must match the QueryRequest shape (it must have a query text field).

Trim spaces off the question.

If nothing is left...

...reject it with error 400 ("bad request") instead of wasting an AI call.

That thread_id is the thread you'll pull on all through Module 3: it's how clicking Approve two minutes later reconnects to this exact half-finished investigation.

02

Meet the Specialists

The "agent" is really four focused roles passing one shared chart between them.

A hospital ward, not a genius

It's tempting to picture one all-knowing AI. In reality, the backend runs a state machine of separate steps. Each step is a specialist with its own instructions, and they all read and write the same patient chart.

🔍
diagnose

The examining doctor. Read-only tools only. Writes the diagnosis and raises a YES/NO flag: does anything need changing?

☑️
select_issues

The triage desk. Only shows up when more than one problem was found, so you can pick which to fix.

📝
propose_remediation / propose_retry

The surgeon planning the operation. Writes a 2-4 sentence plan naming the exact tool and arguments.

🛠️
apply_remediation

The surgeon operating. The only step holding write tools: patch, scale, delete, apply YAML.

🩺
verify_remediation

The follow-up check. Waits 15 seconds, re-reads the cluster and answers GOAL_ACHIEVED: YES or NO.

Wiring the flowchart

The whole flowchart is declared in one short file. Each node is registered by name and pointed at a Python function.

app/agent/graph.py 
workflow.add_node("diagnose", diagnose_node)
workflow.add_node("select_issues", select_issues_node)
workflow.add_node("propose_remediation", propose_remediation_node)
workflow.add_node("propose_retry", propose_remediation_node)
workflow.add_node("apply_remediation", apply_remediation_node)
workflow.add_node("verify_remediation", verify_remediation_node)

workflow.set_entry_point("diagnose")
PLAIN ENGLISH

Box 1, "diagnose", runs the diagnosis function.

Box 2, "select_issues", is the triage pause.

Box 3 drafts the first fix plan.

Box 4 drafts a retry plan, using the same function under a different name.

Box 5 actually changes the cluster.

Box 6 checks whether it worked.

 

Every run starts at "diagnose."

💡
Same function, two names: why?

propose_remediation and propose_retry do identical work. Giving them separate names lets the system pause before a retry without pausing before the first proposal. Naming a step is how you get to attach rules to it, a trick worth asking AI for by name ("make it a separate node so I can interrupt before it").

How a paragraph becomes a yes/no

An AI model answers in prose, but code needs a boolean. The trick: the instructions demand the reply end with a fixed line like REMEDIATION_NEEDED: YES, and a regex fishes it out.

app/agent/parsing.py 
def _extract_flag(text: str, flag: str) -> tuple:
    pattern = rf"\s*{flag}\s*[:=]\s*(YES|NO)\b[^\n]*"
    match = re.search(pattern, text, re.IGNORECASE)
    is_yes = bool(match) and match.group(1).upper() == "YES"
    cleaned = re.sub(pattern, "", text, flags=re.IGNORECASE)
    return is_yes, re.sub(r"\n{3,}", "\n\n", cleaned).strip()
PLAIN ENGLISH

Given the model's reply and a flag name like "REMEDIATION_NEEDED"...

...describe the pattern: the flag name, a colon or equals sign, then YES or NO.

Look for it anywhere, ignoring upper/lower case.

It's a YES only if the line was found and says YES. Missing flag = NO (the safe default).

Cut that line out so the user never sees the robot-speak.

Hand back the yes/no plus the tidied-up report.

Then a tiny router function reads those flags and picks the next box:

app/agent/nodes.py 
def route_after_diagnose(state: AgentState) -> str:
    if not state.get("remediation_needed"):
        return END
    if len(state.get("issues", []) or []) > 1:
        return "select_issues"
    return "propose_remediation"
PLAIN ENGLISH

After diagnosis, decide where to go.

If nothing needs changing (a read-only question)...

...stop here and just show the report.

If more than one separate problem was found...

...go to triage so the human picks.

Otherwise, go straight to drafting a fix.

⚠️

If your own agent keeps giving advice instead of acting, this pattern is the fix to request.

Pausing for a Human

How an investigation freezes mid-flight, waits for your click, and picks up exactly where it stopped.

The save point

In a video game you hit a save point, switch off the console, and the next day you're standing in the same room with the same inventory. This agent does the same thing between "here's my proposed fix" and your Approve click, which might come seconds or hours later.

1

Agent runs until it reaches a guarded step

→
2

Whole state saved under the session's thread_id

→
3

HTTP request finishes; you see Approve / Reject

→
4

Your click loads the save and continues

The "save" is called a checkpoint, and the thing that stores it is the checkpointer.

Where the pauses are declared

One line decides which boxes need a human's permission before they run.

app/agent/graph.py 
checkpointer = build_checkpointer()
compiled_graph = workflow.compile(
    checkpointer=checkpointer,
    interrupt_before=["select_issues", "apply_remediation", "propose_retry"] if REQUIRE_APPROVAL else [],
)
PLAIN ENGLISH

Set up storage for save points (database or memory; see next screen).

Turn the flowchart into a runnable program...

...that saves its state after every step...

...and stops just before triage, applying a fix, or retrying, but only if approval is required. If REQUIRE_APPROVAL is "false", the list is empty and it never stops.

Done.

⚠️
One environment variable removes the human

Set REQUIRE_APPROVAL=false and /api/query runs diagnose → fix → verify in a single request, with an AI changing your cluster unsupervised. The deploy guide says to leave it "true". When an AI suggests "just flip this flag to simplify," you now know what it costs.

Where the save file lives

The checkpointer picks its storage based on one environment variable.

app/infra/checkpointer.py 
def build_checkpointer():
    database_url = os.getenv("DATABASE_URL")
    if not database_url:
        logger.warning("DATABASE_URL not set - using in-process MemorySaver (state lost on restart, not shared across replicas).")
        return MemorySaver()
PLAIN ENGLISH

Decide where to keep save points.

Is there a database address configured?

If not...

...log a loud warning: saves live only in this one program's memory. A restart wipes them, and a second copy of the server can't see them.

Use the in-memory store. (Otherwise the rest of the function connects to Postgres through a connection pool.)

🧠

MemorySaver

Fine on your laptop. Lost on restart. Invisible to other replicas.

🐘

PostgresSaver

Survives restarts. Any replica can resume any session. Needed in production.

When to stop retrying

After every verification, a router picks one of four outcomes and counts it as a metric.

app/agent/nodes.py 
def route_after_verify(state: AgentState) -> str:
    if state.get("goal_achieved"):
        REMEDIATION_OUTCOMES.labels(outcome="succeeded").inc()
        return END
    if state.get("blocked"):
        REMEDIATION_OUTCOMES.labels(outcome="blocked").inc()
        return END
    if state.get("attempt", 0) >= MAX_ATTEMPTS:
        REMEDIATION_OUTCOMES.labels(outcome="exhausted").inc()
        return END
    REMEDIATION_OUTCOMES.labels(outcome="retrying").inc()
    return "propose_retry"
PLAIN ENGLISH

After verifying, decide what's next.

Fixed?

Count a "succeeded"...

...and stop.

Was the action refused by a hard rule?

Count "blocked"...

...and stop, because trying again would be refused identically.

Out of attempts (default 3)?

Count "exhausted"...

...and stop.

Otherwise count a "retrying"...

...and go draft a new plan, with notes on what already failed.

retry_context"--- Attempt 1 --- Applied: ... Verification: ..." so the next plan avoids repeating a failure
/api/guidanceAdds "--- Human guidance for the next attempt ---" which the planner is told overrides its own judgment
conversation_historyPast turns are stored labelled "[earlier reply - historical, may be out of date]" so old refusals aren't repeated

Tools and Guardrails

How an AI "uses" Kubernetes, and the safety interlocks that stop it from doing something dumb.

A tool is a function plus a description

The model can't run code. What it gets is a menu: each tool's name, its arguments, and its docstring. The decorator @tool builds that menu entry automatically.

app/tools/read.py 
@tool
def list_namespaces() -> str:
    """List all namespaces in the Kubernetes cluster."""
    try:
        v1 = client.CoreV1Api()
        namespaces = v1.list_namespace()
        ns_list = [ns.metadata.name for ns in namespaces.items]
        return json.dumps({"namespaces": ns_list})
PLAIN ENGLISH

Put this function on the AI's menu.

Its name is what the AI asks for. It takes no arguments and returns text.

This sentence is literally what the AI reads to decide when to use it.

Try the following (and on failure, return an error message instead of crashing).

Get a handle on the Kubernetes "core" API.

Ask it for every namespace.

Keep just the names.

Send them back as JSON text for the AI to read.

👀

24 read tools

diag_tools: get_pod_logs, describe_pod, get_cluster_events, check_permission, get_resource (any kind)...

✍️

11 write tools

remedy_tools: patch_deployment, scale_deployment, apply_kubernetes_yaml, delete_resource...

Who gets what

diagnose, propose and verify get only read tools. Only apply_remediation is handed both.

The ask-run-answer loop

Every specialist runs the same short loop: ask the model, run whatever tools it requested, feed the results back, repeat. A hard cap (8 rounds for diagnosis) stops it from investigating forever.

app/agent/nodes.py (diagnose_node) 
    for _ in range(limit):

PLAIN ENGLISH

Repeat at most limit times (8 here).

Send the whole conversation so far to the model.

Count the tokens it used, for the cost display.

Did it ask for any tools?

...look the name up in the read-only tool list. (A write tool name simply won't be found here.)

Made-up tool name?

Safety interlocks in the write tools

A table saw has a blade guard and a kill switch because a sharp tool plus a distracted operator is dangerous. The write tools carry the same kind of interlocks, written in Python so the model can't talk its way past them.

🪪

No self-promotion

Can't edit its own ServiceAccount, ClusterRole or bindings. That would let it grant itself more power.

🏛️

System namespaces

kube-system and friends: hands off while healthy, allowed only once something is confirmed broken.

🔁

Pointless restarts

Refuses to restart a pod failing with ImagePullBackOff or a missing ConfigMap. A fresh copy fails the same way.

🧍

Orphan pods

Won't delete a standalone pod unless recreating=true.

💽

Live storage

Refuses to delete a Bound PersistentVolume, and won't delete Nodes at all.

📍

No guessing "default"

Namespaced writes without a namespace are refused instead of silently landing in the wrong place.

💡
In an agent, error messages are prompts

A human reads "Error 403" and investigates. A model reads the error and decides its next move. That's why these refusals say why, whether it's permanent ("This is permanent, not a transient error"), and what to do instead. Vague errors make agents retry the same wrong thing.

Prompts written as scar tissue

The instructions to the model are long, and many rules end with a story: "A real deployed test had this exact failure..." Each one is a bug that happened, got diagnosed, and was turned into a rule.

Events ≠ nowStale events said a ConfigMap was missing. It existed. The agent "fixed" a non-problem. Rule: always read the live object.
max-ns ≠ maxA PVC was created in "default" instead of "max-ns" and reported as success. Rule: copy namespaces exactly; tools refuse to guess.
Gone ≠ fixedA Pending standalone pod was deleted and reported "Fixed". Rule: a missing resource is never success.
Role ≠ permissionA Role listed the verb, but with the wrong apiGroup. Rule: verify RBAC with check_permission (a real "can-i" check).

To make "events are history" stick, get_cluster_events even looks up each event's object live and tags it "GONE - object no longer exists, this event is stale". Code does what the prompt alone couldn't guarantee.

A related gap: not every refusal stops the retries

apply_remediation marks a result BLOCKED only when the text contains "is not in the allowed set". A guard refusal like "controls this agent's own permissions" doesn't match, so the loop can burn all 3 attempts on something that will never be allowed. When you ask AI to change refusal wording, ask it to check what code matches on that text.

The outside brain: two model settings

Both specialists use Amazon Nova Pro by default, but with different temperature. Model IDs come from environment variables, so swapping models needs no code change (but does need re-testing, as Module 2 showed).

Smoke detectors: health probes

Kubernetes keeps asking the backend "are you OK?" using two probes. Liveness failing restarts the pod; readiness failing just stops sending it traffic.

app/main.py 
@app.get("/readyz")
def readiness():
    try:
        k8s_client.CoreV1Api().list_namespace(limit=1, _request_timeout=3)
    except Exception as e:
        logger.warning(f"readiness check failed: kubernetes api unreachable: {e}")
        raise HTTPException(status_code=503, detail=f"kubernetes api unreachable: {e}")
    try:
        bedrock_client.meta.region_name
    except Exception as e:
        logger.warning(f"readiness check failed: bedrock client misconfigured: {e}")
        raise HTTPException(status_code=503, detail=f"bedrock client misconfigured: {e}")
    return {"status": "ready"}
PLAIN ENGLISH

Answer Kubernetes' "ready for traffic?" check at /readyz.

 

Try a real, tiny request:

list one namespace, giving up after 3 seconds.

If that fails...

...log it...

...and answer 503 "not ready."

Then check Bedrock:

read the client's configured region. This never contacts AWS. It only proves the client object was built.

If even that fails...

...log it...

...and answer 503.

Otherwise: ready.

💡
Read the code, not the README

The README says /readyz "checks Kubernetes API and Bedrock client connectivity." The Kubernetes half is a real network call; the Bedrock half isn't. A pod can report Ready while every Bedrock call fails with bad credentials. Catching gaps like this, between what docs (or an AI) claim and what code does, is a core skill.

Keycards: RBAC and NetworkPolicy

RBAC controls what the agent can do to the cluster; NetworkPolicy controls who it can talk to over the network.

Where it breaks (and how to tell)

These are the failure modes visible in the code and deploy notes. Each one has a fingerprint you can recognise.

1
Pod stuck in CreateContainerConfigError

configmap.yaml alone lacks AWS_REGION, the model IDs and REQUIRE_APPROVAL. Those are merged in by Kustomize's configMapGenerator. Deploy with kubectl apply -k k8s/, not -f manifests/.

2
Pod exits immediately on start

entrypoint.sh runs a preflight check: missing required env vars, no in-cluster config, or an unreachable Postgres stops it with a clear message. Read kubectl logs.

3
Every Bedrock call fails with InvalidClientTokenId on EKS

Access keys in the Secret override Pod Identity in boto3's credential chain. Leave them commented out on EKS.

4
list_secrets works locally but errors in the cluster

Locally the backend uses your kubeconfig (often admin). In the cluster it uses the ServiceAccount, whose ClusterRole doesn't grant reading secrets, so the API answers 403 Forbidden.

5
Approve spins, then a gateway timeout

Each request runs synchronously. With verify sleeping 15s and up to 3 attempts, one call can take minutes. If you enable the Ingress, its default proxy timeout (60s on ingress-nginx) may cut it off first.

🪞
The agent could diagnose its own outage

Failure #1 is exactly the kind of problem the agent is built to catch: a pod waiting on a missing ConfigMap key. But a guard keeps it out of its own namespace while things are healthy, and it can't reason at all while its own pod won't start. Some problems still need a human with kubectl.
